## 共同执行约定与顺序

1. 三人从确认后的同一 main 基线建立个人分支，使用个人克隆、仓库级 Git 身份和个人镜像标签。共享小内存云主机的构建按顺序进行。
2. 各人在个人目录执行完整 before/after/verify；A、B 同时完成各自机制说明与测试。测试选题先检查已有覆盖，发现实现问题再做必要修改。
3. A、B 向 C 交付文档、测试、提交 SHA 和个人证据索引。C 汇总后重新构建并完成集成验收，A/B 交叉审阅最终证据。
4. 状态使用 TODO、DOING、DONE、BLOCKED。DONE 必须附可检查的产物和实际验证结果；BLOCKED 写明原因与下一步。

## 分支、个人目录与云主机镜像管理

Git 分支用于管理源码和个人贡献，Docker 镜像标签用于管理构建结果。切换 Git 分支不会自动切换或更新镜像；不同分支使用同一镜像标签构建时，后一次构建会覆盖该标签的指向。

| 对象 | 管理目的 | 本组约定 |
|---|---|---|
| Git 分支 | 隔离个人代码、测试与提交 | A/B/C 分别使用 `e6/a`、`e6/b`、`e6/c`，均从同一个已确认的 main 基线创建 |
| 个人克隆目录 | 隔离工作区、分支切换和运行证据 | 每人在云主机自己的学号目录中独立克隆，不在同一工作目录交替切分支 |
| 个人镜像标签 | 避免共享 Docker 中的标签相互覆盖 | 使用 `course1027-buildchecker:自己的学号`；构建与运行均显式指定同一标签 |
| 源码 SHA 与镜像 ID | 追溯实际构建和运行版本 | 正式运行记录完整源码提交 SHA、镜像标签及镜像 ID；标签可变化，不能单独作为版本证明 |

执行顺序：

1. 确认个人工作区中的修改已妥善保存，同步 main，记录三人共同起点，再创建各自分支。
2. 各自在个人克隆内修改、提交和构建个人镜像。新增测试或实现改动后重新构建，避免运行旧镜像；正式留证时使用已提交的源码版本。
3. 在自己的镜像与全新 work 输出目录中完成验证，保存个人贡献和证据索引，通过个人 PR 交付给 C 集成。
4. 贡献合并到 main 后，C 同步最终 main，在自己的克隆中重新构建个人标签的镜像，记录最终源码 SHA 和镜像 ID，再完成 C06 的完整验收。
5. 最终归档引用集成版本的证据；个人开发分支的结果作为个人复现与贡献记录保留。共同 GitHub 仓库和 main 持续沿用。

本约定不要求为云端环境另建长期分支。若确有云端适配修改，应在个人分支中说明原因、审阅差异并决定是否合入 main，避免正式验收使用未说明的环境专用源码。

## 本仓库运行入口

以下在 Linux 云主机个人克隆的 `A-buildchecker/` 中执行，先将 SID 设置为自己的学号；每次使用新的输出目录。手册中的 course.py 在本仓库对应 lab_cloud.py，并需显式指定个人镜像。

```bash
SID=自己的学号
python3 scripts/lab_cloud.py build --image "course1027-buildchecker:$SID" --out work/e6-build --build-timeout 3600
python3 scripts/lab_cloud.py e6 --image "course1027-buildchecker:$SID" --out work/e6-before
BEFORE_CODE=$?
printf 'BEFORE_EXIT_CODE=%s\n' "$BEFORE_CODE"
python3 scripts/lab_cloud.py e6 --fixed --image "course1027-buildchecker:$SID" --out work/e6-after
AFTER_CODE=$?
printf 'AFTER_EXIT_CODE=%s\n' "$AFTER_CODE"
python3 scripts/verify_e6_evidence.py --before work/e6-before/evidence/findings.json --after work/e6-after/evidence/findings.json > work/e6-verify.json
cat work/e6-verify.json
diff -u work/e6-before/fixture/Makefile work/e6-after/fixture/Makefile
```

修复前 CLI 返回 1 表示发现问题；修复后返回 0。diff 检出预期差异时返回 1。保留报告里的 status 与 clean/build 退出码，不能只凭 CLI 判断运行失败。

## 提交物边界

- Git：机制说明、个人记录、测试或必要实现修改、实验报告、证据索引和贡献记录。个人新增测试及实现修改经个人分支提交。
- 归档：最终修复前后完整目录、构建/测试日志、两图、进程、findings、原始 trace、Make 数据库、输入副本、diff、校验输出，以及源码和镜像版本记录。work 被忽略时，必须另行交付完整证据，不能只给目录名。
- 归档外：最终压缩包 SHA256；最终 PR 与合并信息可在单独提交说明中补充，无需为追记自身最终提交号反复开 PR。
- E7 接续：完整重复性验证、故障注入、完整 gate 和 CI 门禁在 E7 验收；E6 新增测试需实际运行，后续纳入 E7。
