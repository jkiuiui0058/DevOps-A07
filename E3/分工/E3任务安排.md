# E3 测试基线任务安排

## 1. 工作原则

- A、B 使用同一个最小 GNU Make/C 项目模板，但在不同目录完成实验，避免修改同一份源码或 Git 历史。
- A 负责固定版本中的 Missing Dependency（MD）和 Redundant Dependency（RD）基线。
- B 负责 C0、C1、C2 连续提交及增量构建基线。
- C 负责统一 Linux/Docker 环境、云端复现、契约校验和最终打包。
- E2 已确定的 Job、Finding、ERROR_REPORT、Artifact URI 和双方责任边界直接复用，不在 E3 重新设计。
- A、B 各自保证实验内容正确；C 负责复现与验收，不代替 A、B 修改实验语义。

## 3. 角色边界

### 3.1 A 必须明确

- 采用的 GNU Make/C 项目及固定版本。
- 构建目标、构建命令、clean 命令和功能验证命令。
- MD 与 RD 对应的 target、dependency 和判断依据。
- 人工答案覆盖的文件范围，尤其是否排除系统头文件。
- 项目是课程最小样例还是论文复现项目。
- 论文项目只能作为附加真实案例，不能替代可稳定重跑的最小基线。

### 3.2 B 必须明确

- C0、C1、C2 各自只改变什么。
- baseline 和 target 的对应关系。
- C1 的预期 MD。
- C2 的编译命令变化。
- 构建产物如何跨版本保留。
- 哪些步骤允许 clean，哪些步骤必须保留旧产物。

### 3.3 C 必须明确

- 统一 Linux 发行版、CPU 架构和工具版本。
- Docker 镜像或云服务器环境的重建方法。
- 统一运行入口、证据目录和日志格式。
- A、B 材料的接收检查项。
- 最终压缩包目录、文件来源和验收结果。

## 4. A、B 向 C 的交接

### 4.1 A 向 C 提供

- `fixtures/md-rd/` 完整源码。
- Makefile、构建命令、clean 命令和运行命令。
- 项目来源、固定 commit 和许可证信息。
- MD/RD 人工标准答案及其来源标记。
- 预期输出与本地实际日志。
- 复现文档：说明目录结构、前置环境、执行顺序、每一步命令、预期输出，以及出现偏差时如何判断 MD/RD 是否仍被正确触发。
- 独立运行 README。

### 4.2 B 向 C 提供

- C0、C1、C2 完整 Git 历史。
- 三个 tag、完整 SHA 和版本差异。
- `repository.bundle` 或其他能够恢复完整历史的文件。
- 编译命令快照。
- 增量构建与 clean build 对照日志。
- 人工预期结果。
- 更新后的 INCREMENTAL_CHECK 请求和响应样例。
- 复现文档：说明如何恢复 Git 历史、切换 C0/C1/C2、区分增量构建与 clean build 的执行顺序、每一步命令与预期输出，以及哪些步骤必须保留旧产物。
- 独立运行 README。

### 4.3 问题退回原则

- MD/RD 行为或人工答案错误，由 A 修改。
- C0/C1/C2 历史、SHA 或增量行为错误，由 B 修改。
- Docker、云服务器、统一脚本、证据索引或打包错误，由 C 修改。
- C 不直接修改 A、B 的实验逻辑，以免人工答案与源码版本失配。

## 5. 与 B07 的确认安排

### 5.1 是否需要确认

需要在 A07 完成内部复现、C 完成初步打包之后，请 B07 做一次交付可消费性确认。该确认不是重新审批项目选型，也不是重新讨论 E2 契约。

不建议在 A、B 尚未完成或 C 尚未复现时就要求 B07 确认，因为此时只能确认设想，无法确认真实 SHA、报告和构建命令是否可用。

### 5.2 提交给 B07 的确认材料

- 项目仓库地址和固定 commit。
- C0、C1、C2 的 SHA。
- 构建、clean 和功能验证命令。
- 一份真实 FULL_CHECK 请求样例。
- 一份真实 INCREMENTAL_CHECK 请求样例。
- 一份真实 ERROR_REPORT 样例。
- Artifact URI 示例及对应读取位置。
- Linux/Docker 工具版本。
- MDFixer 所需的源码版本、Makefile 版本和报告之间的对应关系。

### 5.3 请 B07 只确认以下事项

- B07 能否读取 A07 提供的 Artifact。
- MDFixer 能否消费该 ERROR_REPORT。
- ERROR_REPORT 是否能定位到正确源码和 Makefile 版本。
- DRAFT 交付内容能否映射为 A07 的 FULL_CHECK 输入。
- 构建与验证命令在双方约定环境中是否明确。

### 5.4 不需要再次确认的 E2 内容

- FULL_CHECK、INCREMENTAL_CHECK 的任务类型和字段。
- 异步 Job 模型及状态语义。
- baseline、target 的基本含义。
- Finding 和 ERROR_REPORT Schema。
- 检测到 MD/RD 时任务仍可为 `SUCCEEDED`。
- `artifact://pair07/...` 的 URI 语法。
- Artifact 的 HTTP 读取、完整性校验和保留规则。
- DRAFT 到 FULL_CHECK 的字段映射。
- A07 负责 BuildChecker、EChecker，B07 负责 DRAFT、MDFixer。

### 5.5 B07 反馈处理

- 如果 B07 确认可以消费，C 将确认记录放入最终实验包。
- 如果只是项目名称、SHA、命令或文件路径错误，由对应负责人修正，不改变公共契约。
- 只有现有 E2 字段无法表达真实实验、MDFixer 无法消费报告或 Artifact 读取方式失效时，才重新协商契约并补充 ADR。
- 如果截止前未收到 B07 回复，C 保存发送材料、时间和当前状态，不能将“等待回复”写成“已确认”。

## 7. C 的打包验收清单

- [ ] README 能说明如何一条命令运行全部实验。
- [ ] A 的 MD/RD 源码、人工答案和行为日志完整。
- [ ] B 的 C0/C1/C2 历史可恢复，tag 与 SHA 正确。
- [ ] C0 clean 输出 `10`。
- [ ] C1 clean 输出 `12`，并存在预期 MD。
- [ ] C2 普通增量输出 `12`，clean 输出 `19`。
- [ ] 环境、工具版本、镜像 ID 和运行 ID 已记录。
- [ ] FULL_CHECK 和 INCREMENTAL_CHECK 使用真实版本信息。
- [ ] 正向 Schema 样例通过，反例被拒绝。
- [ ] B07 的确认记录或待确认状态已如实保存。
- [ ] 失败实验保留日志、原因、尝试和下一步。
- [ ] 压缩包不包含密钥、Token、密码和个人配置。
- [ ] 压缩包不包含无关缓存和无法解释的临时文件。

## 8. 最终完成条件

E3 完成不以“代码能够编译”作为唯一标准。最终应同时满足：

1. A 的 MD/RD 人工答案有可重复的行为证据。
2. B 的 C0/C1/C2 是真实、连续且可恢复的 Git 历史。
3. C 能在统一 Linux/Docker 或云端环境中重新运行全部实验。
4. E2 契约能够承载真实项目、真实 SHA 和真实报告。
5. B07 已完成交付可消费性确认，或者仓库如实记录了待确认状态和已发送材料。
6. 最终实验包能够由未参与开发的人按照 README 独立重跑。
